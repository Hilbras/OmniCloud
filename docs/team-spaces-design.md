# Team spaces — sharing model (design)

Status: design only. No team-space code exists. This document is the
prerequisite the feature plan requires before implementation, and it records the
open decisions that block it.

## Goal

Let several accounts share a folder tree with roles, without the server learning
file contents or (for OCE2 files) display names.

## What already exists

- **Per-user root key (URK).** Generated on first use, wrapped by a recovery code
  or a device-pairing secret. It never reaches the server.
- **OCE1 files.** Content is encrypted with a per-file DEK; the DEK is wrapped by
  a key derived from the URK. The server sees ciphertext plus an authenticated
  manifest. Metadata (name, MIME type, description) is encrypted inside the
  envelope.
- **OCE2 files.** Same envelope, but the _server-visible_ file name is replaced by
  an opaque token; the real name lives only in the user's local encrypted name
  index.
- **Share links.** A one-time link wraps the file DEK under a random secret kept
  in the URL fragment; the server stores only the wrapped DEK. This works per
  file, not per folder.

## The OCE2 conflict

OCE2 hides names by keeping them out of the server's reach. A shared space needs
every member to see the same names. Two options:

1. **Space-scoped name key.** Names in a space are encrypted to a key every
   member holds. OCE2 files moved into a space must be re-encrypted (name and
   metadata) to that key, and the local-only index entry is retired.
2. **No OCE2 inside spaces.** Spaces accept OCE1/plaintext only; OCE2 files must
   be migrated first, with an explicit warning that the migration is one-way.

Option 1 is the correct long-term model but requires a metadata re-encryption
pass and a migration tool; option 2 is cheaper but splits the product into two
incompatible sharing modes. **No decision has been made**, and the plan forbids
writing code before one is recorded.

## Proposed key model

- Each space has a **space key (SK)**, generated by the creator.
- Each member's device receives SK wrapped under a key derived from that member's
  URK (`wrap(SK, KEK_urk)`), stored server-side as an opaque blob per member.
  The server can hand out the blob but cannot open it.
- File DEKs inside the space are wrapped under SK (not the uploader's URK), so a
  member who joins later can decrypt every file without the uploader being
  online.
- Removing a member: generate SK', re-wrap every file DEK under SK', wrap SK' for
  the remaining members, and drop the removed member's blob. This is a
  background, resumable job — the same shape as the planned key-epoch rotation.
- The removed member keeps the ability to decrypt ciphertext they already
  fetched (unavoidable without re-encrypting all content). New writes are
  unreadable to them. This must be stated in the UI, not hidden.

## Roles

| Role   | Read | Upload / new version | Invite / remove | Delete space | Audit |
| ------ | ---- | -------------------- | --------------- | ------------ | ----- |
| Owner  | yes  | yes                  | yes             | yes          | yes   |
| Editor | yes  | yes                  | no              | no           | yes   |
| Viewer | yes  | no                   | no              | no           | no    |

Enforcement is server-side on every route, and the UI mirrors it. A viewer with
the SK can still decrypt what they downloaded; the role bounds the API, not
cryptography.

## Server data sketch

```
Space(id, name, ownerId, createdAt, deletedAt)
SpaceMember(spaceId, userId, role, wrappedSpaceKey, joinedAt, removedAt)
SpaceFolder(spaceId, folderId)            -- or Folder.spaceId
SpaceAudit(spaceId, actorId, action, targetId, at)
```

Files gain a nullable `spaceId`; a file belongs to at most one space. The
existing `Storage` record stays per user — spaces do not share a Telegram
channel, so each member's uploads land in their own storage. That keeps the
storage provider and quota model unchanged.

## API sketch

- `POST /api/spaces` — create; returns the space and the creator's wrapped SK.
- `POST /api/spaces/:id/invites` — one-time invite; the secret stays in the URL
  fragment, exactly like device pairing and share links.
- `POST /api/spaces/:id/members` — accept an invite by uploading a wrapped SK for
  the joining member.
- `GET /api/spaces/:id/members` — metadata only.
- `DELETE /api/spaces/:id/members/:userId` — starts the re-wrap job.
- `GET /api/spaces/:id/files` — listing, authorized by role.
- Re-wrap job status: `GET /api/spaces/:id/rotation`.

## Invariants to test before shipping

1. A member who was never given SK cannot decrypt a file (wrong-key failure, no
   plaintext fallback).
2. Removing a member makes new uploads undecryptable for them.
3. An interrupted re-wrap resumes without leaving a file wrapped under both keys
   or under neither.
4. Viewer role cannot upload, invite or delete, even with a valid session.
5. OCE2 files cannot enter a space until the chosen name strategy is
   implemented; the API refuses them explicitly.
6. A member leaving the space does not delete the owner's files.

## Why this is not implemented yet

- The OCE2 name strategy is undecided (see above).
- The re-wrap job is the same machinery as key-epoch rotation, which is itself
  pending and needs crypto review.
- It is an explicitly optional phase ("larger bet") in
  [`future-features-plan.md`](future-features-plan.md).

No server-side code should be written until the OCE2 decision and the rotation
job exist.
